# Этап 4. Приложения с фиксированным тиком на железе + уточнение эффекта KSM под нагрузкой

## План

Статус: **утверждён владельцем 2026-11-19** с рекомендованными ответами на вопросы 1–4. Этап 3 владелец принял 2026-11-19 без претензий. Временный sudoers остаётся на этот этап (решение владельца).

**Цель этапа.** Ответить на третий уровень темы (кейс приложений реального времени) и закрыть слабое место этапа 3: «KSM не меняет p99 под нагрузкой» сейчас означает только «эффект меньше разрешения опыта».

1. **Блок 0.** Отвечает на вопрос, можно ли утверждать, что KSM не удлиняет хвост, с заранее заданным порогом.
2. **Блоки А–В.** Отвечают на вопрос, как KSM влияет на длительность тика, 1 % low и пропуски тиков у реальных серверов (Luanti, Godot headless) и у синтетического тик-сервера, и связаны ли всплески с COW и ksmd.

### Почему не просто «20–30 повторов»

Оценка по данным этапа 3 (бутстреп-перевыборка повторов, `stage3-load-per-run.csv`, устойчивая фаза):

| Нагрузка | p99 при KSM выкл. | полуширина 95 % ДИ разности, n=10 | n=30 (оценка) |
|---|---|---|---|
| Python 50 запр./с | 1.8 мс | ±1.5 мс | ±0.6 мс |
| JVM 400 запр./с | 0.25 мс | ±0.4 мс | ±0.02 мс |
| Python 200 запр./с | 2.8 мс | ±2.2 мс | ±1.4 мс |
| JVM 1600 запр./с | 0.37 мс | ±0.85 мс | ±0.2 мс |

Оценку для n=30 получили перевыборкой из 10 значений, поэтому она оптимистична. Главный источник разброса — дрейф между прогонами: нагрев, фон рабочего стола, перебои питания. Порядок прогонов в этапе 3 — циклический сдвиг списка вариантов (поправка 2026-11-19: раньше здесь было «случайный»), анализ шёл по независимым группам, и разность медиан включала этот дрейф. Отсюда решение: **парный дизайн плюс больше пар**, а вывод формулируется как **тест эквивалентности**, а не как «незначимо».

### Шаг 0. Доработки (без замеров, отдельными коммитами)

1. **Закрепление условий в скрипте, а не договорённостью** (урок блока Г, Л12–Л13). Обёртка серий `scripts/series-guard.sh`:
   - на время серии ставит `auto_battery=off` и `lid_profile_*=performance` в `powersave.conf`, при любом выходе возвращает из бэкапа (как `stage3-night.sh`);
   - preflight получает проверки: профиль performance, `power-auto` не включит экономию, отметка `ac_online`.
2. **`hw_sampler.py`: столбцы `ac_online`, `lid`, `power_profile` раз в 1 с.** Тогда метки «прогон задет перебоем питания» считаются для каждой серии автоматически, а `stage3-power-flags.py` станет общей функцией сводок.
3. **Парный режим в `stage2-load.sh`** (`PAIRED=1`): порядок — случайно переставленные **пары** (on, off) или (off, on), стоящие подряд. Повторы получают номер пары. Сводка считает разность внутри пары: медиана разностей, бутстреп по парам, знаковый тест Уилкоксона.
4. **Закреплённые образы:** сборки и запуски по digest (`env/native/images.txt`), чтобы не повторилась разница версий (Л9).

### Шаг 1. Блок 0 — эквивалентность под нагрузкой (~8 ч, ночь)

- Python 50 и JVM 400 запр./с (частоты ВМ, прямое сравнение с этапом 3), **30 пар** на нагрузку. Это 120 прогонов, ~4 мин каждый.
- **Порог эквивалентности задаётся до опыта** (вопрос 2 владельцу): по умолчанию ±20 % от p99 при KSM выкл., на логарифмической шкале.
- **Правило вывода:** если 90 % бутстреп-ДИ отношения p99 вкл./выкл. (по парам) целиком внутри [0.83; 1.20], то эффект меньше порога. Это TOST, два односторонних теста на уровне 5 %. Тот же анализ — для p99.9 и p50, в фазах merge и steady.
- Атрибуция (ksmd во всплесках) — повтор находки этапа 3 на новых данных. Это прямая проверка её воспроизводимости.

### Шаг 2. Серверы с тиком — подготовка (агент, без замеров)

Три нагрузки, у каждой 8 одинаковых контейнеров, KSM через `prctl` на запуске, как в этапах 1–3:

| | Что | Тик | Как меряем тик |
|---|---|---|---|
| **Синтетический** | свой C-сервер `workloads/ticksrv` (на основе тика репетиции): фиксированный тик 60 Гц, мир в памяти (общий снимок + свои изменения), запись в K страниц на тик | 16.7 мс | сам пишет t_wake, t_done каждого тика |
| **Luanti** | `luanti-server` 5.17 (Arch extra) в контейнере на базе `archlinux`, одинаковый мир у всех 8, мод-нагрузка: сущности и изменения блоков в активной зоне | `dedicated_server_step` 0.05 с (20 Гц) | Lua-мод: `core.register_globalstep` + `core.get_us_time()` → журнал dtime и работы шага |
| **Godot headless** | `godot` 4.7 `--headless`, проект: физика 60 Гц, N тел, состояние в памяти | 16.7 мс | GDScript `_physics_process`: `Time.get_ticks_usec()` в начале и в конце |

Метрики (по прогону и фазе pre/merge/steady):
- длительность тика p50/p99/p99.9;
- **1 % low** — средний темп самых медленных 1 % тиков, в тиков/с, как в метриках кадров;
- доля пропущенных тиков (интервал > 1.5 периода);
- джиттер (стандартное отклонение и IQR интервала);
- атрибуция всплесков к `cow_ksm` и ksmd на ЦП (`scripts/lib/attribution.py`).

У Luanti нет штатного безголового клиента. Нагрузку создаёт мод внутри сервера, а не игроки (вопрос 3). Это ограничение пойдёт в limitations.

Каждую нагрузку проверить дымовым прогоном. Проверить, что мир действительно сливается (`ksm_stat` контейнеров) и что тик пишется без потерь.

### Шаг 3. Блок А — пилот серверов (~1 ч)

Сначала калибровка с KSM выкл., по восемь контейнеров на нагрузку. Цель — медиана работы тика в устойчивой фазе в пределах 20–50 % номинального периода. Из подходящих конфигураций с долей пропусков не выше 1 % выбираем ближайшую к 35 %. Для выбора используются только данные KSM выкл.

Затем по одной паре KSM вкл./выкл. на выбранной настройке каждой нагрузки с трассировкой. Проверяем, что нагрузка укладывается в заданный диапазон и слияние сохраняется. Выбор фиксируется в `docs/decisions.md` до основной серии.

### Шаг 4. Блок Б — основная серия серверов (~5 ч 50 мин машинного времени)

3 нагрузки × **15 пар** KSM вкл./выкл., без привязки. Это 45 пар, 90 прогонов. Фазы 30/60/90 с, прогрев 10 с, стабилизация 25 с, запуск контейнеров и выгрузка трассы. Серия делится на дневные части по целым повторам. Настройки нагрузки и тепловых измерений — Р25 и Р26.

### Шаг 5. Блок В — привязка ksmd для синтетического сервера (~2 ч)

Варианты `shared`, `sibling`, `split`, `unpinned` (как ksmd-pin этапа 3), 10 повторов. Связывает механизм этапа 3 с метриками кадров. Только синтетический сервер: у Luanti и Godot много потоков, привязать «тик» к одному ЦП нельзя.

### Шаг 6. Отчёт этапа

Сводки, графики [нативные графики](../figures/png/native/), журнал, limitations, коммит, остановка. Для полного запуска `scripts/stage4-ticks-pipeline.sh` последовательно выполняет остаток Б, блок В и итоговый анализ. Итоговые материалы по двум сериям сохраняются в `docs/stage-4-results.md` после проверки полноты и целостности данных.

### Условия чистоты замеров

- Крышку не закрывать во время серий (Л13). Ноутбук на зарядке. Перебои разъёма пишутся в `hw.csv`, задетые прогоны помечаются и проверяются тестом чувствительности (как в этапе 3).
- Серии запускаются службами `systemd-run --user` через `series-guard.sh`. Анализ — только после серии (Л7).

### Бюджет

Исходная оценка машинного времени: блок 0 — 8 ч, А — 1 ч, Б — около 5 ч 50 мин, В — около 2 ч. По окончании блока А осталось 130 прогонов и около 8 ч машинного времени, без учёта дневных пауз и итоговой обработки. Диск проверяется перед запуском каждой части.

### Вопросы к владельцу

1. Блок 0 — обе нагрузки (Python и JVM, ~8 ч) или только Python (~4 ч, единственный эффект на ВМ)? Рекомендую обе: у JVM самая сильная атрибуция.
2. Порог эквивалентности: ±20 % от p99 (рекомендую), или абсолютный (например, ±0.5 мс), или оба?
3. Нагрузка Luanti создаётся модом внутри сервера, без настоящих клиентов. Устраивает? Альтернатива — писать бота протокола Luanti: это долго и выходит за рамки KSM.
4. Образы на базе `archlinux` для Luanti и Godot: ~0.5–1 ГБ загрузки. Можно?

## Блок 0 — результаты

На нативном Arch измеряли задержки HTTP-запросов для Python и JVM, по 8 контейнеров на нагрузку. Частоты на контейнер — 50 и 400 запросов/с соответственно. Замеры 19–20 ноября дали 30 полных пар Python и 31 пару JVM. Прерванная пара Python исключена, повторно снятая пара JVM № 4 в другом куске учтена как отдельная пара по Р24.

В таблице парная оценка отношения задержек KSM вкл./выкл. и 90 % бутстреп-ДИ. Оценка — экспонента медианы логарифмов отношений внутри пар. Заранее заданная зона эквивалентности — [1/1,2; 1,2]. Для вывода об эффекте используется 95 % ДИ (Р24). Контрольная фаза pre, когда KSM ещё выключен в обоих прогонах, прошла проверку эквивалентности по всем шести сочетаниям нагрузки и метрики. Оценки отношений в ней лежали в диапазоне 0,928–1,024.

| Нагрузка | Фаза | p50 | p99 | p99.9 |
|---|---|---|---|---|
| Python | Слияние | 1,038 [0,998; 1,171] | 1,172 [0,883; 1,255] | 1,130 [0,945; 1,280] |
| Python | Устойчивая | 0,993 [0,928; 1,054] | 1,028 [0,787; 1,189] | 1,093 [0,876; 1,189] |
| JVM | Слияние | 1,062 [1,033; 1,103] | 1,158 [1,042; 1,562] | 1,069 [0,984; 1,162] |
| JVM | Устойчивая | 1,072 [1,041; 1,094] | 1,126 [1,003; 1,225] | 1,193 [1,114; 1,237] |

- **p50** эквивалентна во всех фазах у обеих нагрузок, включая анализ без перебоев питания.
- **Основная метрика p99.** Для Python обе рабочие фазы и для JVM устойчивая фаза дали неопределённый результат. Для JVM в фазе слияния 95 % ДИ [1,024; 1,562] исключает единицу на всех парах (Уилкоксон p = 0,224). После исключения пар с перебоями питания 95 % ДИ [0,975; 1,562] включает единицу.
- **Вторичная метрика p99.9.** В устойчивой фазе JVM оценка роста +19,3 %, 95 % ДИ отношения [1,100; 1,238], Уилкоксон p = 0,0066. На подвыборке без перебоев оценка +17,2 %, 95 % ДИ [1,029; 1,233], Уилкоксон p = 0,085. В фазе слияния JVM p99.9 эквивалентна в обеих выборках. Для Python в устойчивой фазе p99.9 эквивалентна на всех парах, а на подвыборке без перебоев результат неопределённый (90 % ДИ [0,939; 1,257]). В фазе слияния результат неопределённый в обеих выборках.
- **Перебои питания** затронули 29 из 68 прогонов третьего куска, суммарно 3263 с на батарее, режим экономии не включался. Для проверки чувствительности остались 20 пар Python и 22 пары JVM. Кроме изменений для JVM p99 и Python p99.9, в контроле Python p99 и p99.9 на подвыборке 90 % ДИ вышли за верхнюю границу зоны эквивалентности (1,242 и 1,260).
- **Связь всплесков с ksmd.** Медианное отношение доли времени ksmd на ЦП во всплесках (запросы с задержкой ≥ p99) к случайным окнам — 1,47–1,66 по нагрузкам и рабочим фазам. Отношение больше единицы в 122 из 124 наблюдений «прогон KSM вкл. × фаза», p < 10⁻⁸ в каждой группе по тесту Уилкоксона. Это связь по времени.

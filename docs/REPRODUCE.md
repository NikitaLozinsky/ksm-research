# Воспроизведение экспериментов KSM

## 1. Методика

- Исходные измерения хранятся в `results/raw/`. Для нового анализа используйте отдельные сводки.
- Основные конфигурации измеряются минимум в 10 повторах. В отчётах приводятся медиана и IQR или доверительный интервал.
- Состояние между прогонами сбрасывают скрипты. Условия опыта, параметры и ограничения записываются вместе с результатом.
- Длинные серии запускаются пользовательской службой через `scripts/series-guard.sh`. Для нагрузочных серий с обработчиком завершения используется `scripts/stop-series.sh`.
- Сбор и анализ проводят раздельно. Фоновые сборки и тесты во время замеров меняют нагрузку на систему.

[Методические решения](decisions.md) · [Ограничения](limitations.md) · [Архивы и данные](DATA.md)

## 2. Требования к машине

| Что | Минимум | Зачем |
|---|---|---|
| ОС | Arch Linux (или производный), ядро ≥ 6.4 | `PR_SET_MEMORY_MERGE` (prctl) появился в 6.4; исходная работа — ядра 7.2–7.3 |
| ЦП | ≥ 4 логических ядра | 8 контейнеров + генератор нагрузки + сэмплеры |
| ОЗУ | ≥ 8 ГБ | 8 контейнеров JVM; сторож прерывает серию при `MemAvailable < 2000 МиБ` |
| Диск | ≥ 30 ГБ свободно | сырые трассы ~1–3 ГБ на серию, образы ~2 ГБ |
| Питание | ноутбук — на зарядке, крышка открыта | перебои питания пишутся в `hw.csv` и помечаются, но лучше без них |
| sudo | временно без пароля (шаг 3) | скрипты пишут в `/sys/kernel/mm/ksm`, `/proc/sys/vm`, запускают `perf` |

Можно и в ВМ (так шли этапы 0–2), но хвосты задержки в ВМ в 17–7700 раз длиннее (итоги этапа 3). Тип системы определяется сам (`systemd-detect-virt`).

**Отличия железа, которые надо проверить, а не предполагать:**
- **AMD вместо Intel:** `scripts/lib/hw_sampler.py` читает счётчики троттлинга `/sys/devices/system/cpu/cpu*/thermal_throttle/` и температуру пакета (coretemp). На AMD их может не быть — столбцы будут пустыми. Это не ломает серию, но отметить в `docs/limitations.md`.
- **SMT (гиперпоточность):** `ksmd-pin` добавляет вариант `sibling` только если есть SMT. Без SMT вариантов меньше — это нормально.
- **Число ЦП:** контейнеров всегда 8, при 4 ЦП машина будет перегружена сильнее — частоты подбирать пилотом (шаг 5), а не копировать.
- **Не ноутбук:** нет `/sys/class/power_supply/AC*` — столбец `ac_online` пустой, метки питания не сработают; это нормально.
- **Нет программ владельца** (`~/bin/power-auto`, `~/.config/powersave/`): `series-guard.sh` и `preflight.sh` это переносят, просто пропускают свою часть. Но на ноутбуке **самому** выключить автоэкономию от батареи (TLP, power-profiles-daemon, auto-cpufreq) на время серий или убедиться, что зарядка не пропадает.

## 3. Перенос и установка

### 3.1. Получение проекта

Клонируйте этот репозиторий в `~/ksm-research`. Часть скриптов использует этот путь напрямую. Образы и бинарники собираются на новой машине (шаг 3.5).

### 3.2. Разделение исходных и новых результатов

Свежие серии получают собственные каталоги `results/raw/<серия>/<дата-время>/`. Сводкам новой машины давайте отдельный префикс (шаг 7). Перед сбором снимка окружения сохраните копию исходного снимка из `env/native/` или `env/vm-oracle/`.

### 3.3. Пакеты

```bash
sudo pacman -S --needed podman stress-ng sysstat perf asciinema tmux jq python-numpy python-pandas python-matplotlib python-scipy nodejs jdk-openjdk htop gcc linux-docs rt-tests man-db man-pages poppler
```
Не Arch: те же пакеты из своего менеджера; `linux-docs` нужен для `Documentation/admin-guide/mm/ksm.rst` своей версии ядра.

### 3.4. Временный sudo без пароля

```bash
sudo ~/ksm-research/scripts/sudo-setup.sh install
```
Проверка — `scripts/sudo-setup.sh status`. **После всех серий удалить:** `sudo ~/ksm-research/scripts/sudo-setup.sh remove`.

### 3.5. Сборка бинарников и образов

```bash
cd ~/ksm-research
workloads/ksm-probe/build.sh
workloads/loadgen/build.sh
scripts/build-workloads.sh
```
`build-workloads.sh` качает базовые образы (nginx, postgres, alpine) и собирает образы нагрузок из `workloads/apps/*`; digest пишутся в `env/<тип>/images.txt`. Сравнить с `env/native/images.txt`: версии приложений должны совпадать (иначе — запись в limitations, как Л9).

### 3.6. Проверка системы

```bash
scripts/preflight.sh
```
Нужен итог `FAIL=0`. Каждый WARN прочитать: «loadavg высокий» — закрыть фоновые приложения и повторить.
Перед замерами закрыть всё лишнее, не пользоваться машиной во время серий. Фоновую активность фиксируйте при калибровке.

## 4. Как запускать серию (общий шаблон)

```bash
systemd-run --user --unit=ksm-<имя> --collect --setenv=PATH="$PATH" [--setenv=ПЕРЕМЕННАЯ=значение ...] \
    bash ~/ksm-research/scripts/series-guard.sh <команда серии>
```
- Короткие серии (минуты) через `scripts/run-all.sh` можно запускать и в tmux: `scripts/tmux-run.sh <имя> scripts/run-all.sh <серии...>`, ждать — `scripts/tmux-wait.sh <имя>` (печатает только итог).
- Ход нагрузочной серии: `~/ksm-research/scripts/watch-series.sh` (шкала, %, время до конца, питание, температура).
- Журналы: `results/logs/<имя>.log`, `.status`, код выхода — `.exit`. Конец — появился `.exit` с `0`.
- Список серий этапов 0–2 с длительностью: `scripts/run-all.sh --list`; план без запуска: `scripts/run-all.sh --dry-run <серии>`.

## 5. Порядок повтора

Длительности — с исходной машины, на другой будут иными. После каждой серии: сводка (шаг 7), запись в журнал, коммит.

| № | Серия | Команда | Время | Что проверяет |
|---|---|---|---|---|
| 1 | trace-check, mps-check, fork-check | `scripts/run-all.sh trace-check mps-check fork-check` | ~7 мин | tracepoint-ы KSM, max_page_sharing, учёт после fork |
| 2 | inherit | `scripts/run-all.sh inherit` | ~65 мин | **наследует ли `PR_SET_MEMORY_MERGE` fork/exec в контейнере** — основа всего метода (Р11 в `docs/decisions.md`). Если на новом ядре не наследуется — СТОП, сообщить владельцу |
| 3 | jitter, xcheck | `scripts/run-all.sh jitter xcheck` | ~80 мин | шум таймера в простое — базовая линия машины |
| 4 | ksm-probe, cow-cost | `scripts/run-all.sh ksm-probe cow-cost` | ~60 мин | KSM на проверочной нагрузке, цена COW KSM-страницы |
| 5 | rehearsal | `scripts/run-all.sh rehearsal` | ~100 мин | модель тика 60 Гц, атрибуция всплесков к ksmd |
| 6 | workloads, factors | `scripts/run-all.sh workloads factors` | ~10 ч | экономия памяти 5 нагрузок × N контейнеров, факторы KSM |
| 7 | loadgen-check | `scripts/run-all.sh loadgen-check` | ~3 мин | генератор нагрузки на эталоне, ожидается `ИТОГ: PASS` |
| 8 | **load-pilot** | `scripts/run-all.sh load-pilot`, затем `scripts/stage2-load-pilot-summary.py` | ~25 мин | **подбор частот запросов для этой машины** |
| 9 | ksmd-tlb, ksmd-pin | `scripts/run-all.sh ksmd-tlb ksmd-pin` | ~2 ч | привязка ksmd к ЦП и сбросы TLB |
| 10 | load, блок Г этапа 3 | см. ниже | ~11 ч | p99 под нагрузкой, 5 нагрузок, KSM вкл./выкл. |
| 11 | блок 0 (этап 4) | см. ниже | ~8 ч | эквивалентность KSM вкл./выкл., парный дизайн, 30 пар |

**Частоты запросов (№ 8).** На исходной машине (ВМ и нативно) использовались nginx 400, Python 50, Node.js 200, JVM 400, PostgreSQL 200 запр./с на контейнер. Правило выбора — по сводке пилота: наибольшая частота, при которой нагрузка ещё **не насыщена** (p99 не растёт скачком, нет отказов). Для сравнимости с исходными данными прогнать **и** исходные частоты, **и** подобранные, если они различаются. Выбор записать в `docs/decisions.md` до основной серии.

**№ 10 — load (блок Г этапа 3):** серии `stage3-load` (nginx 400, Python 50, JVM 400), `stage3-load-np` (Node.js 200, PostgreSQL 200), `stage3-load-high` (nginx 1600, Python 200, JVM 1600), по 10 повторов, KSM вкл./выкл., прогрев JVM под нагрузкой 60 с (Р22). Всё это делает один скрипт (частоты — в его последних строках; если пилот дал другие, менять там отдельным коммитом):
```bash
systemd-run --user --unit=ksm-blockG --collect --setenv=PATH="$PATH" \
    bash ~/ksm-research/scripts/series-guard.sh ~/ksm-research/scripts/stage3-blockG.sh
```
Перед ним — `scripts/stage3-blockG-prep.sh` (прочитать шапку: что он готовит).

**№ 11 — блок 0** (Python 50 и JVM 400 запр./с; частоты зашиты в строке `env ... RATE_PYTHON=50 RATE_JVM=400` в `scripts/stage4-block0.sh` — переменными окружения их не переопределить. Если пилот показал насыщение при этих частотах, поменять там отдельным коммитом и записать в `docs/decisions.md` до серии):
```bash
systemd-run --user --unit=ksm-s4b0 --collect --setenv=PATH="$PATH" \
    bash ~/ksm-research/scripts/series-guard.sh ~/ksm-research/scripts/stage4-block0.sh
```
Сначала дымовой прогон (~8 мин): то же с `--setenv=SMOKE=1`.
Кусками (например, только днём): `--setenv=REP_START=1 --setenv=REP_END=13`, затем `REP_START=14` (до 30). Каждый кусок — новый каталог серии, анализ склеивает куски (шаг 7).

**Этап 4, серверы с тиком (ticksrv, Luanti, Godot)** — на исходной машине код ещё не написан; план — `docs/stage-4.md`, шаги 2–5. Не начинать без плана владельца.

## 6. Если что-то пошло не так

- Серия упала или ПК перезагрузился: следующий `preflight.sh` покажет оставшиеся контейнеры эксперимента (метка `ksm-research=1`), `reset_state` их удалит. Чужие контейнеры не трогаются.
- Вернуть KSM вручную: `echo 2 | sudo tee /sys/kernel/mm/ksm/run`, затем прежние значения из блока `ksm` первого `params.json` серии.
- Пустой прогон (нет `lat-c*.csv.gz`) — анализ его отбрасывает; отметить в журнале.
- Что меняют скрипты в системе и как возвращают — таблица в `docs/running-native.md`.

## 7. Сводки и анализ (после конца серии)

Каждой сводке новой машины — префикс с именем ПК, чтобы не перезаписать исходные `results/summary/*`:
```bash
cd ~/ksm-research
scripts/stage2-load-summary.py results/raw/<серия>/<каталог> <пк>-<серия>
```
Сводки этапов 0–1 — `scripts/stage*-summary.py` с тем же именем, что у серии (аргументы — в шапке каждого скрипта).

Блок 0 (несколько кусков):
```bash
scripts/stage4-paired-analysis.py <пк>-stage4-eq \
    results/raw/stage4-eq/<каталог1>=<пк>-stage4-eq-part1 \
    results/raw/stage4-eq/<каталог2>=<пк>-stage4-eq-part2
```
Результат — `results/summary/<пк>-stage4-eq-paired.csv`: вердикт TOST ±20 % по нагрузке, фазе, метрике. Порог ±20 % задан до опыта, **не менять** после просмотра данных.

Сравнение с исходной машиной — по тем же метрикам и формулам (`scripts/stage3-compare.py` — пример сравнения ВМ и железа). Графики — `figures/<этап>-<метрика>.png` + `.svg`, 300 dpi, подписанные оси, разброс по повторам.

Архив трасс после серии (большие файлы не в git): `scripts/archive-traces.sh <каталог серии>`.
